# HTML → Sitecore Content SDK Conversion Instructions

## Project Context

Convert HTML-based website **sections** into **Sitecore Content SDK** React components for the **BQ** Next.js App Router app in this repository (`bq/`). Target: near pixel-perfect visual match (screenshots win), **section-by-section** incremental migration — not greenfield page routes.

**Source compatibility:** Live HTML (View Source), capture bundles (`.bq/captures/…`), static exports, WordPress/CMS HTML output, Webflow exports, or any rendered HTML. Convert the **browser HTML**, not PHP/Django/Rails source.

**AI assistant context:** Written for Cursor / Claude / compatible agents. Follow this file when converting HTML into Sitecore-ready components in `bq/`.

**Wired into `create:sectioncomponents`:** The pipeline always appends to the codegen system prompt: `bq/tools/create-section-components/prompts/content-sdk-conversion-bridge.md` + `prompts/references/FieldCatalog.reference.tsx` (unstyled field/placeholder patterns). Codegen v2 also attaches matching component-type `*.reference.tsx` primers. The shared Azure user prefix always includes host `section-registry/content-families.json` (detected content families).

**Not this workflow:** Do **not** run `create-next-app`, invent `app/about/page.tsx` routes, or treat this as a standalone Next.js marketing site. Routing, layout, editing, and content already live in XM Cloud + Content SDK.

## Conversion Workflow

### Phase 1: Pre-Conversion Setup (one-time)

The Next.js + Content SDK app **already exists**. Do not scaffold a new project.

1. **Work inside `bq/`**
   ```bash
   cd bq
   cp .env.example .env.local   # if needed; never commit secrets
   npm install
   npm run dev
   ```

2. **Know the real structure** (not `app/page.tsx` per marketing URL):
   ```
   bq/
   ├── src/
   │   ├── app/[site]/[locale]/[[...path]]/page.tsx   ← Sitecore catch-all (do not add routes per HTML page)
   │   ├── components/{collection}/ComponentName/    ← YOUR conversion output lives here
   │   │   ├── component-name.tsx
   │   │   ├── component-name.definition.ts
   │   │   └── optional: *.client.tsx, *.visual.tsx
   │   ├── lib/cache/                                ← getSitecorePage, etc.
   │   └── Layout.tsx / Providers.tsx
   ├── sitecore.config.ts
   ├── next.config.ts
   └── .sitecore/component-map.ts                    ← regenerated by tooling
   ```

3. **URL → Sitecore page mapping** (planning only)

   | Source URL | What you convert | Where it lands |
   |------------|------------------|----------------|
   | `https://example.com/` | Sections on home | Components + page presentation seeds in definitions |
   | `https://example.com/about` | Sections on about | Same — **not** `src/app/about/page.tsx` |
   | Header / footer chrome | Shared partials | Reusable components on partial designs / layout placeholders |

   **Pattern:** One HTML **section** → one Sitecore **component** (plus child components when composites). Pages are composed in Sitecore via placeholders, not Next.js file-based routes.

   **Home presentation invariant (enforced by `create:sectioncomponents` + emit):**

   For a home capture, these three counts must match for **page-body** bands (chrome stays on Partial Designs only):

   `count(detected sections with role=page) === pages.home.renderings.length === count(Home.yml headless-main parent renderings)`

   The pipeline sorts `pages.home` by `detected-sections.json`, fails closed if any detected page/partial band is unwired, refuses to replace home with a thinner set on incomplete `--only` runs, and refuse to emit `__Renderings` when a wired `definitionKey` has no rendering item id. Do not hand-edit presentation or `Home.yml` to “fix” gaps — re-run create + `definitions:generate` / `authoring:generate`.

4. **Capture input (preferred when available)**
   - Section HTML + screenshots from capture tooling (`bq/tools/capture`, `.bq/captures/…`)
   - `section-information.json` / suggested fields when present
   - Desktop → tablet → mobile crops for layout fidelity

**CRITICAL:** Do not create project subfolders or a second Next.js app. Edit `bq/src/components/…` only.

### Phase 2: Per-Section Conversion (single scope)

**⚠️ CRITICAL: SINGLE SECTION / COMPONENT SCOPE**

You convert **exactly one section** (or one named component) per task.

**PROHIBITED:**

- ❌ Fetching or converting other pages linked from the HTML
- ❌ Creating new App Router page files for each URL
- ❌ Hand-authoring or editing `authoring/items/**/*.yml`
- ❌ Hardcoding marketing copy in JSX when it belongs in Sitecore fields
- ❌ Importing `@sitecore-content-sdk/nextjs/config-cli`, `/tools`, or `/client` inside components
- ❌ Copying `<script>`, GTM, chat widgets, JSON-LD into components

**ALLOWED:**

- ✅ Convert provided HTML / capture for the current section only
- ✅ Preserve href values on links (map to General Link fields)
- ✅ Emit `*.tsx` + `*.definition.ts` following existing siblings
- ✅ Note media URLs for definition seeds (Content Hub / absolute URLs OK)

Linked pages and other sections are separate tasks.

#### Step 1: Extract source HTML

**Need rendered HTML**, not backend templates.

| Method | When |
|--------|------|
| **A. Capture bundle** | Preferred for pixel-perfect work — use `section.html` + screenshots |
| **B. Live URL** | Single section URL / page; still convert **one section** |
| **C. View Source / outerHTML** | Manual paste of the section root |
| **D. curl** | `curl URL > section.html` — current page only |

#### Step 2: Classify complexity

| Type | Indicators | Action |
|------|------------|--------|
| **Static field-driven** | Text, images, links; no interaction | Server component + Content SDK fields |
| **Client chrome** | Accordions, carousels, menus, forms | Split: server `*.tsx` + `'use client'` `*.client.tsx` when needed |
| **Composite** | Repeating cards / columns in a parent | Parent + child components + `AppPlaceholder` / placeholders in definition |
| **Variants** | Same model, 2+ structural presentations | Named exports (`Default`, `Promo`, …) + `variants` in definition |
| **Shared chrome** | Site header/footer | Extract as shared components; wire via partial designs / layout |

Identify type in analysis, then proceed.

#### Step 4: HTML → JSX + Content SDK fields

Apply standard JSX transforms **and** Sitecore field binding.

| HTML | Content SDK / JSX |
|------|-------------------|
| `class="…"` | `className="…"` |
| Void tags | Self-close: `<br />` |
| `onclick` / `onchange` / `for` | `onClick` / `onChange` / `htmlFor` (client file) |
| Visible copy | `<Text field={fields.Headline} tag="h1" />` |
| Rich HTML body | `<RichText field={fields.Body} />` |
| `<img>` content images | `<Image field={fields.Image} className="…" />` |
| `<a href>` content CTAs | Childless `<Link field={fields.Link} />` or `<Link … showLinkTextWithChildrenPresent={false}>…</Link>` when wrapping children |
| Self-closing text-only Link | `<Link field={fields.Link} />` — **omit** `showLinkTextWithChildrenPresent` (SDK already paints field text) |
| Decorative arrow on simple CTA | Tailwind `after:content-['→']` on **childless** Link — never nest `→` as a React child |
| Comments | `{/* … */}` |

**Hard rules for this repo:**

1. Typed `Fields` interface; `ComponentProps & { fields: Fields }` from `lib/component-props`.
2. `const { fields } = props;` before using `fields`.
3. `const params = props.params ?? props.rendering?.params ?? {};` then `renderingId = params.RenderingIdentifier \|\| params.id` — never `props.id`.
4. Root element: `key={renderingId \|\| props.rendering?.uid}` and `id={renderingId \|\| undefined}`.
5. Export named variants: at least `export const Default`.
6. Always mount field components for declared fields (Pages editing) — do not skip empty fields with `fields?.X &&`.
7. No hardcoded marketing strings in JSX; seeds live in `definition.content`.

**Minimal server component shape:**

```tsx
import { Text, Image, Link } from "@sitecore-content-sdk/nextjs";
import type { ImageField, LinkField, TextField } from "@sitecore-content-sdk/nextjs";
import { ComponentProps } from "lib/component-props";

interface Fields {
  Title: TextField;
  Logo: ImageField;
  Link: LinkField;
}

type Props = ComponentProps & { fields: Fields };

export const Default = (props: Props) => {
  const { fields } = props;
  const params = props.params ?? props.rendering?.params ?? {};
  const renderingId = params.RenderingIdentifier || params.id;

  return (
    <article
      key={renderingId || props.rendering?.uid}
      id={renderingId || undefined}
      className="flex w-full …"
    >
      <Image field={fields.Logo} className="…" />
      <Text field={fields.Title} tag="h3" className="…" />
      <Link
        field={fields.Link}
        className="… after:ml-3 after:content-['→']"
      />
    </article>
  );
};
```

#### Step 5: CSS → Tailwind (Sitecore AI breakpoints)

Convert styling to Tailwind. Prefer utilities; arbitrary values (`bg-[#09051c]`, `max-w-[650px]`) when brand tokens demand it.

**Breakpoint contract (required):**

| Band | Width | Tailwind | Sitecore AI crop |
|------|-------|----------|------------------|
| Mobile | `< 768` | default / `max-md:` | **370px** |
| Tablet | `768–1023` | `md:` … below `lg:` | **768px** |
| Desktop | `≥ 1024` | **`lg:`** for desktop layout switches | **1024px** (Desktop Small) |

**Hard:** Unlock multi-column / side-by-side desktop chrome with **`lg:`**, not `md:`. Tablet must not receive desktop columns. Prefer screenshot composition over inventing a generic card layout. Avoid `xl:` as the primary desktop switch unless an existing component already does.

Match typography, spacing, and color to crops; use page design notes only as brand guidance when they do not fight screenshots.

---

#### Step 6: Assets & media

| Source | Target |
|--------|--------|
| Content images / logos in capture | Seed `Image` fields with delivery URLs (e.g. Content Hub) in `definition.content` |
| Decorative icons (SVG inline) | Prefer inline SVG / Lucide if already used — keep non-authorable chrome out of fields |
| Brand static assets needed locally | `bq/public/…` with leading-slash paths — rare for content images |
| External CDN | OK when that is the production source of truth |

Do **not** force everything into `/public/images` when Sitecore media / Content Hub is the real source. Authors edit Image fields in Pages.

---

#### Step 7: Definition (`*.definition.ts`)

Every converted component needs a `kind: "component"` definition (see `bq-definitions` skill + `kind-recipes.md`).

**Must include:**

- `definitionKey`, `name`, `displayName`, `componentName`, `icon` (via `sitecore-icons`)
- `collectionSystem` / `siteSystem` (e.g. `sitecore` / `sitecore-com`)
- `model.folderTemplate` + `model.itemTemplate` (spaced Title Case names)
- Field types: `Single-Line Text`, `Multi-Line Text`, `Rich Text`, `Image`, `General Link`, etc.
- `datasourceLocation` + `content.location` folders (spaced Title Case)
- `content.culture` = capture language; `cultures` for other locales
- `content.items[]` seeds (path-safe `name`, human `displayName`, field values)
- `variants: [{ name: "Default" }, …]` matching TSX exports
- `placeholders` when composite

**Never** create/edit/delete YAML under `authoring/items/`. Run:

```bash
npm run authoring:generate
```

---

#### Step 8: Component extraction timing

| When | Action |
|------|--------|
| First occurrence | Inline in the section component |
| Repeats 2–3× with same structure | Extract child component + placeholder wiring |
| Site-wide header/footer | Dedicated chrome components + client file for menus |

Composites: seed **one content item per visible child** in screenshots; parent holds section chrome only (Heading/Subtitle).

### Phase 3: Dynamic content (Sitecore-first)

| Old HTML / backend idea | This project |
|-------------------------|--------------|
| `<?php echo $title ?>` / `{{ title }}` | Sitecore field → `<Text field={…} />` |
| CMS page body | Rich Text / nested components in placeholders |
| Product listing from DB | Datasource items + optional GraphQL / wildcard helpers (see existing Dom Security patterns) |
| “Hardcode for now” | Seed `content.items` in definition — still field-driven in TSX |
| WordPress posts export | Sitecore data items via definitions, not `/data/*.json` pages |

**Data fetching in the app:**

- **Published pages:** `getSitecorePage` / cache helpers in `src/lib/cache/` — do not call `client.getPage` from random components for layout.
- **Preview / editing:** `draftMode` + `client.getPreview` / Design Library — never wrap preview in `'use cache'`.
- **Component-level lists:** Prefer datasource children / placeholders; advanced cases may use existing `src/lib/wildcard` patterns — do not invent a parallel data layer.

---

### Phase 4: Interactivity & forms

- Interactive UI → `'use client'` in `*.client.tsx` (or whole file if small and already client).
- Keep field rendering on the server component when possible; pass fields/props into client chrome.
- Forms: React state + API route under `src/app/api/` only when the product needs it; do not assume PHP `action="/contact"`. Prefer existing consent / search patterns in the codebase.
- Accordions/carousels: match capture behavior at tablet/mobile (e.g. accordion below `lg` when crops show it).

---

### Phase 5: URLs, redirects, SEO

| Concern | Where it lives |
|---------|----------------|
| Page URLs | Sitecore items + site definition — not `app/about/page.tsx` |
| Redirects | Sitecore redirect items + Content SDK `RedirectsProxy` in `src/proxy.ts` |
| Locale / multisite | `[site]` / `[locale]` + next-intl (`${site}_${locale}`) |
| robots / sitemap | `src/app/api/robots`, `src/app/api/sitemap` (Content SDK route handlers) |
| next.config redirects | Only for host-level edge cases — not the primary SEO map |

Do not generate a giant `next.config.js` redirects list as the default migration path.

## Troubleshooting

| Symptom | Fix |
|---------|-----|
| Component missing in Pages | Regenerate component map; check `componentName` / definitionKey kebab match |
| Empty on site | Datasource not wired / presentation seed missing — fix definition content + regenerate |
| `className` hydration mismatch | Dynamic classes only on client; avoid invalid HTML nesting |
| Link text doubled | Childless Link (omit prop) for field text; with children use `showLinkTextWithChildrenPresent={false}` and visible copy from Title/CTAText/icon only |
| Desktop looks like tablet | Use `lg:` for desktop columns, not `md:` |
| YAML drift / validate fails | Fix `*.definition.ts`, re-run `authoring:generate` — never patch YAML |
| Preview wrong / stale | Preview uses uncached client APIs; check draftMode and revalidate tags for published |
| Build fails on `props.id` | Use `params.RenderingIdentifier` pattern above |
| Forbidden import | Only main `@sitecore-content-sdk/nextjs` in components |

## Quick reference

**Core principles**

1. HTML section → Sitecore component (TSX + definition), not Next.js `page.tsx`  
2. CSS → Tailwind with Sitecore AI breakpoints (`lg:` = desktop)  
3. Copy/media/CTAs → Content SDK fields + definition seeds  
4. One section per task; preserve hrefs; do not crawl the site  
5. Authoring via definitions + generate — never hand-edit YAML  

**Decision tree**

- Static fields? → Server component + `Text` / `Image` / `Link` / `RichText`  
- Interaction? → `*.client.tsx`  
- Repeating cards? → Child component + placeholders + N content seeds  
- Two structural looks? → Named variants + matching exports  
- New URL? → Sitecore page item / presentation — not a new App Router folder  

**Quality gate:** type-check/build green, fields editable in Pages, visual match at 370/768/1024, authoring generate clean.

## Anti-patterns

### ❌ Converting whole sites in one go  
One section at a time; verify visually before the next.

### ❌ Adding `app/<slug>/page.tsx` for each HTML page  
Use Sitecore routes + placeholders.

### ❌ Hardcoding copy in JSX “like a static Next site”  
Breaks Pages editing and localization.

### ❌ Editing generated YAML  
Definitions only → `authoring:generate`.

### ❌ Premature shared packages across starters  
BQ components stay under `bq/src/components/`; do not symlink to `examples/`.

### ❌ Treating `md:` as desktop  
Desktop layout switches use `lg:` (≥1024).

### ❌ Duplicate CTA labels inside `<Link>`  
Childless Link paints field text; Links with children always use `showLinkTextWithChildrenPresent={false}` (children = sole visible UI).

### ❌ Copying live-site scripts into components  
No GTM/chat/JSON-LD in section TSX.

### ❌ Greenfield `create-next-app` / public-only asset migration as the default  
This app already exists; media usually belongs in Sitecore / Content Hub seeds.
